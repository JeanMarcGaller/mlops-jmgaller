# GitHub Actions CI

## Role in the Project

The GitHub Actions workflow provides automated quality checks for the repository.

It runs linting, formatting checks and the full test suite on GitHub whenever code is pushed or a pull request is opened.

This helps ensure that changes do not break code quality or existing tests.

## Trigger Events

The workflow runs on:

```yaml
push:
pull_request:
```

This means CI is executed for:

* every push
* every pull request

## Job

The workflow defines one job:

```yaml
lint-and-test
```

It runs on:

```yaml
ubuntu-latest
```

## Workflow Steps

### Check out repository

```yaml
uses: actions/checkout@v4
```

This downloads the repository content into the GitHub Actions runner.

### Install uv

```yaml
uses: astral-sh/setup-uv@v5
```

This installs `uv`, which is used for dependency management and command execution.

### Set up Python

```yaml
run: uv python install 3.12
```

This installs Python 3.12 for the CI environment.

### Install dependencies

```yaml
run: uv sync --dev
```

This installs project dependencies including development dependencies such as:

* pytest
* ruff
* pre-commit related tooling
* pytest-cov if configured as dev dependency

### Ruff lint

```yaml
run: uv run ruff check .
```

This checks code style and linting rules.

### Ruff format check

```yaml
run: uv run ruff format --check .
```

This verifies that files are formatted correctly.

It does not modify files in CI. It only fails if formatting is needed.

### Run tests

```yaml
run: uv run pytest
```

This runs the full test suite.

## Quality Gates

The CI workflow requires all three checks to pass:

```text
ruff check
ruff format --check
pytest
```

If any of these fail, the CI job fails.

This makes CI the automated equivalent of the local quality command:

```bash
make quality
```

## Test Strategy

The tests are designed to run in CI without real external service calls.

They use local test data and mocking for components that would otherwise call:

* Open-Meteo
* Hopsworks
* Model Registry
* Feature Store

This keeps CI fast, reproducible and independent of secrets.

The workflow does not require a `.env` file because tests should not depend on real Hopsworks credentials.

## Key Design Decisions

### CI Uses `uv`

The same tool used locally is also used in CI.

This keeps dependency installation and command execution consistent across local development and GitHub Actions.

### CI Does Not Use Secrets

The workflow does not configure Hopsworks credentials or Open-Meteo runtime settings.

This is intentional because unit tests should not depend on external services.

### Formatting Is Checked, Not Applied

CI uses:

```bash
uv run ruff format --check .
```

This ensures formatting problems are caught without modifying files in the CI runner.

### Single Simple Job

The workflow uses one job for linting, formatting and tests.

This keeps the setup easy to understand and sufficient for the project size.

## README-Relevant Points

* The repository includes a GitHub Actions CI workflow.
* CI runs on push and pull request.
* CI installs dependencies with `uv`.
* CI checks Ruff linting.
* CI checks Ruff formatting.
* CI runs the pytest test suite.
* Tests are designed to run without real Hopsworks or Open-Meteo calls.
* CI does not require secrets.

## Limitations / Future Work

* CI currently runs only on Python 3.12.
* CI does not run coverage reporting.
* CI does not build the Docker image.
* CI does not run end-to-end Hopsworks pipelines.
* A future version could add a Docker build check.
* A future version could upload coverage artifacts.
* A future version could run a small smoke-test subset separately.
